    Runtime and storage qualification — 6 November 2026

    This study addresses D06 through measured changes. Separate stages reserve retained histories, remove profiled per-step vector copies and let progress workers wait between display updates. No simulation equation or operation order changes in these stages.

    Storage change

    Simulation::setup knows the complete positive-time sample count. It now reserves that count for time and each engaged matrix/source-current history. It does not instantiate unrequested histories. Output decimation, trace labels, history contents, retry reconstruction and public class layouts remain.

    The memory guide derives the raw payload 8*N*(1+U+S). Vector growth can add transient copies and allocator overhead; unused capacity is not necessarily resident memory. The results below measure actual peak RSS rather than treating a capacity ratio as a RAM reduction.

    std::bad_alloc and std::length_error from reservation become a recoverable STORAGE_ALLOCATION_FAILED diagnostic with the requested sample count. The enum value is appended, retaining existing values. A count of 8e18 fits int64 but exceeds any supported vector<double>::max_size(); CLI and repeated C++ recovery tests reject it without attempting an enormous allocation or inducing physical-memory pressure. This check does not promise recovery from an OS OOM kill.

    Method

    The clean source baseline is 8e9515ec5c1cac7e5c2d7e3cfbd81f8dfe67e503. The local Linux run uses GCC 16.2.1, C++17, Release -O3 -DNDEBUG, default static JoSIM/KLU libraries and the host's dynamic C++ runtime. Cache, compiler, kernel, available CPU set, binary hash and candidate diff identity are recorded.

    Eight fixtures exercise:

    • 64 independent DC nodes with 1/8/32 retained voltages, 600,000 internal samples.
    • The same source network with eight requested applied-current histories.
    • The qualified zero-loop-inductance noisy SQUID: 5.1 million samples at 1 ps, fixed seed 1729, 200 MHz bandwidth and 20 ps output sampling.
    • 128 mutually coupled RL pairs, 128 RLC cells and 128 parallel JJs, each with 100,000 internal samples. Dyadic synthetic timesteps make grid counts exact.

    Each binary gets a warmup, followed by seven paired repetitions per fixture, with baseline/candidate order reversed on alternate pairs. All use minimal CLI mode and the same selected CPU. No builds or profiles run concurrently with the final timed campaign. Monotonic time surrounds the child command; captured pipe EOF wakes the supervisor promptly. GNU time independently records wall, user/system CPU and peak RSS. The archive retains medians, quartiles and ranges.

    A provisional wrapper used timeout polling with file-directed stdout, which quantized its supervisor wall time by up to 50 ms. Those wall results are excluded. The final campaign was repeated with the corrected method; its owner hashes distinguish it from the preserved provisional evidence.

    The owner validates finite, strictly increasing samples, exact grids/seeds, analytic DC voltages/source currents, RL/RLC equilibria and symmetric-JJ KCL. The noisy mean has a 3 nV allowance around the independently derived weak-noise RSJ mean; the longer scientific study establishes its model/statistical scope. Every paired CSV hash must match exactly. All 112 timed runs pass these unchanged assertions and all paired outputs are byte-identical.

    Reservation results

    Median wall time and peak resident memory:

    Workload Baseline seconds Reserved seconds Baseline MiB Reserved MiB
    128 JJs 0.3098 0.3110 10.13 10.05
    128 coupled RL pairs 0.6166 0.6166 11.66 10.71
    128 RLC cells 0.3868 0.3866 9.94 9.70
    Eight applied-source histories 0.4318 0.4141 59.63 47.66
    Long noisy SQUID 0.5219 0.5115 102.77 89.45
    One voltage history 0.4055 0.4002 18.97 15.15
    32 voltage histories 0.4780 0.4453 199.77 159.49
    Eight voltage histories 0.4220 0.4132 56.80 47.68

    Peak memory falls about 13% for the noisy run and 20% for 32 voltages or eight applied-current histories. The widest case's wall median falls 6.8%; the worst median wall change is +0.4%. Baseline allocator-dependent RSS varies across repetitions, particularly the eight-history cases; full quartiles are retained rather than presenting one favorable run.

    The initial engineering heuristic sought a 15% noisy-run RSS reduction. That single-workload heuristic was not met. The change is retained for the measured broader 20% storage benefit, 13% noisy-run benefit and negligible runtime cost. The decision receipt states the missed heuristic explicitly; no numerical assertion or performance-regression limit was relaxed. This is a bounded engineering result, not a universal speed or memory guarantee.

    Per-step vector copies

    Callgrind 3.25.1 identified two allocation sites in otherwise read-only loops. For 2,048 steps, a 128-JJ profile performed 262,144 allocations/frees inside handle_jj; a 256-inductor profile performed 524,288 inside handle_inductors. These counts equal one vector copy per device per step. Parser/setup allocations are separate. Removing these copies makes both hot-function allocation counts zero; the profiled CSV outputs remain byte-identical.

    The engine borrows CPR coefficients through Model::cpr_view() and reads the inductor's existing public coupling vector directly. Existing copying getters retain their signatures and behavior. The new CPR accessor returns a const reference tied to its live Model; no class layout or numerical formula changes. The engine does not mutate either collection while using it.

    A separate seven-pair campaign holds reservation constant on both sides, using clean source ca3c516 as its baseline. It repeats the same eight fixtures and assertions with the corrected clock. All 112 timed runs pass and all paired CSVs match exactly:

    Workload Before seconds Borrowed-read seconds Wall reduction
    128 JJs 0.3089 0.2616 15.3%
    128 coupled RL pairs 0.6164 0.4877 20.9%
    Long noisy SQUID 0.5174 0.4780 7.6%

    JJ/coupled-bank CPU medians fall about 17%/21%. The largest wall increase among the other fixtures is 1.4%, within the predeclared 5% regression limit. Peak RSS stays within 1.2% on every case. Both target banks exceed the predeclared 5% improvement requirement. These are separate measurements, not sums of percentage gains from different stages.

    artifacts/audit-resolution/performance/views/ retains the exact comparison owners, all per-run receipts, source/binary identities, profiles and annotated call trees. Its baseline already includes reservation, so these gains isolate the two copying sites through the pure-JJ and pure-inductor fixtures.

    Progress workers

    The clean baseline is 9de8d69a8ff4925ecd0256b5a1e50ecca63e5f7d, which already includes both earlier stages. The old progress worker continually polled atomic values. It now waits up to 20 ms between updates; completion notifies it immediately, so finishing a short run does not require that delay. Internal callers configure text and total before starting the worker.

    Two public-helper defects were reproduced separately: including its header alone failed to compile because of missing includes, and creating two workers then destroying the bar aborted because only the last thread was joined. The header is now self-contained; completion/destruction joins all workers and repeated completion is safe. Installed-consumer and repeated embedding tests protect these contracts. Added synchronization state changes ProgressBar's layout; consumers must recompile. This does not add simulation parallelism.

    A separate seven-pair campaign uses two available CPUs, default progress mode, the same CSV/numerical checks and the corrected clock above. All 42 timed runs pass with identical paired CSVs:

    Workload Before wall seconds Waiting wall seconds Before CPU seconds Waiting CPU seconds
    128 coupled RL pairs 0.5041 0.4939 0.97 0.48
    128 RLC cells 0.3923 0.3853 0.75 0.37
    Five-sample DC run 0.002405 0.002070 below timer resolution below timer resolution

    Both medium cases exceed the predeclared 40% CPU-reduction requirement and have no wall regression. The small-run median adds no latency, within its predeclared 5 ms absolute allowance; its millisecond result is not a general speed claim. Peak RSS changes by at most +0.33% in the medium cases.

    Minimal mode creates no progress worker but still constructs the helper. Another seven-pair campaign repeats all eight earlier fixtures in minimal mode: all 112 timed runs pass, every paired CSV is identical, and the largest median wall increase is 1.06%, within the predeclared 5% regression limit. Peak RSS changes by at most +0.59%. No numerical tolerance was changed. artifacts/audit-resolution/performance/progress/ retains both summaries, per-run receipts, exact owners, fixtures, source/binary hashes and the independent header/lifetime red/green evidence.

    Verification and evidence

    All four local GCC/Clang Debug/Release configurations pass 34/34 CTest groups, including new CLI and repeated embedding storage-limit checks. Full Clang Debug ASan/UBSan and leak detection pass 34/34 in 229.86 s. Native-platform qualification remains required for the pushed revision; it is not inferred from the benchmark's Release runs.

    The vector-copy stage also passes all four local 34/34 suites. Its focused ASan/UBSan/leak campaign passes 9/9 groups in 102.46 s, covering junction, coupling, noise, installed-consumer and recovery paths. Final integrated full sanitizer/native qualification remains required separately.

    The progress stage passes all four local 34/34 suites and full Clang Debug ASan/UBSan/leak detection, 34/34 in 211.29 s. Its fresh installed consumer includes the progress header first and completes a worker twice. Repeated library runs also destroy two-worker bars with and without explicit completion. The preceding vector-copy source passes all ten native binary/library jobs and the utility job in CI42298764991. Each subsequent pushed revision still requires its own native checks.

    artifacts/audit-resolution/performance/reserve/ contains summary.json, the explicit decision.json, all per-repetition receipts, fixtures and exact measure.py/paired_reserve.py owners. Detailed timing logs and CSV witnesses remain under build/audit-resolution/performance/paired-reserve-final/. Baseline/candidate binary and source identities are retained separately.

    To reproduce the archived owner, run from a source checkout. Place the two corresponding Release executables at build/audit-resolution/performance/bin/{baseline,reserve-candidate}, copy its eight fixtures into build/audit-resolution/performance/fixtures/, and place the owners in that performance directory. Run:

    python -B build/audit-resolution/performance/paired_reserve.py

    The result directory must be new; prior results are preserved. This task-owned Linux measurement owner uses GNU time and taskset. It is not part of portable CTest or a claim about runtime on other operating systems.
